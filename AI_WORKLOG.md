# AI_WORKLOG

Як я працював у парі з ШІ-агентом над цим завданням: інструменти, інструкції, ключові промпти й місця, де агент помилявся.

## Інструменти та розподіл ролей

- **Агент:** Claude Code (розширення VS Code), модель Claude Opus 5.5. Субагенти й workflow запускала та сама сесія. Останній раунд незалежного рев'ю і
  виправлень після нього йшов на Claude Fable 5.2.
- **Генератор (бонус):** CLI того самого агента в headless-режимі з моделлю Claude Sonnet, без інструментів, у порожній
  тимчасовій теці. У коді й логах він не названий: команду задає змінна `GEN_LLM_CMD`. Для повторного запуску:

  ```bash
  export GEN_LLM_CMD='claude -p --model sonnet --output-format text --tools "" --no-session-persistence --strict-mcp-config'
  npm run generate -- generator/examples/inputs/TC-GEN-01.txt
  ```

  Якщо генератор запускається зсередини сесії того самого агента, перед командою потрібен `env -u CLAUDECODE`.
- **Людина:** ставить задачу і приймає рішення. Зокрема: робимо за best practices, тонкий POM, публічний репозиторій,
  розпаралелюємо роботу між агентами, жодних згадок інструмента в комітах і коді.
- **Головний агент (головна сесія):**
  - розвідка сайту й API живими пробами;
  - каркас, CI, документація;
  - розподіл роботи між субагентами;
  - **незалежна перевірка** кожного їхнього звіту.
- **Субагенти:** три паралельні виконавці (UI, API, генератор), кожен лише у своїй теці. Далі два workflow
  «посилення → незалежне рев'ю → перевірка знахідок і виправлення».

### Хронологія

1. **Розвідка.** curl по API, Playwright-проба по saucedemo. Знайдено 4 баги UI та 6 багів API ще до першого тесту. Сьомий баг API (дробова ціна обрізається) помітив агент API
   під час написання тестів, а головний агент незалежно відтворив його перед тим, як заводити.
2. **Каркас:** `playwright.config.ts` з проєктами, `tsconfig`, CLAUDE.md з правилами.
3. **Три субагенти паралельно** з розділеним володінням файлами (`tests/ui`, `tests/api`, `generator` +
   `tests/generated`) і окремими `--output` для Playwright, щоб прогони не стирали результати один одного.
4. **Best practices з офіційних джерел**, а не з пам'яті: playwright.dev Best Practices, CI і Annotations,
   правила eslint-plugin-playwright. Звідти:
   - ESLint з `no-floating-promises`;
   - Chromium, Firefox і WebKit;
   - `workers: 1` і `globalTimeout` у CI, трейси `on-first-retry`;
   - дії CI закріплені на SHA, мінімальні `permissions`, Dependabot.
5. **Два workflow.** Посилення, далі рецензент, який не бачить звіту автора (щоб не прив'язуватися до чужого
   висновку), далі виправлення: кожну знахідку спершу намагаються спростувати. Сесія агента під час рев'ю
   обірвалась. Workflow відновили з кешу, а перед цим перевірили за часом змін файлів, що перервані рецензенти
   нічого не зіпсували.
6. **Крос-перевірка** репозиторію проти тексту завдання, документація, push і перевірка першого прогону CI.

## Інструкції для агента

Робочі правила лежать у [CLAUDE.md](CLAUDE.md). Майже кожне правило з'явилося після конкретної помилки
в цій же роботі:

| Правило в CLAUDE.md | Чому воно там |
| --- | --- |
| Немає `waitForTimeout`; лише web-first assertions | Перша проба читала DOM до завершення SPA-навігації (помилка 1) |
| Кожне очікуване значення має джерело | Без цього тест легко «підганяється» під те, що показав застосунок |
| API-тести видаляють усе, що створили, у teardown | Проби залишили бронювання на спільному стенді (помилка 5) |
| Баг-тест: спершу контролі, потім перевірка бага, запаркована через `parkedOn` | Контролі мають падати по-справжньому (помилка 3), а виправлений баг має приходити зеленим, а не червоним «Expected to fail, but passed» |
| Перевірка бага приймає будь-яке коректне виправлення | Інакше після виправлення на 422 замість 400 тест далі «очікувано падає», і фікс ніхто не помітить |
| Ніколи не послаблювати твердження заради зеленого | Генератор має машинний захист від цього (див. [generator/README.md](generator/README.md)) |
| Definition of done: 3 прогони поспіль і тест бачили червоним | Одиночні зелені прогони сховали дві гонки (помилка 6); агент API зловив так мутацію, яка била не в той рядок |
| Коміти без атрибуції інструмента | Моя вимога (див. «Уточнення під час роботи»; помилка 4) |

## Ключові промпти

### 1. Постановка

Текст тестового завдання (UI, API, CI, AI_WORKLOG, README, бонус) я дав агенту дослівно одним повідомленням.

### 2. Уточнення під час роботи

| Промпт | Що змінилося |
| --- | --- |
| «і головне ніяких згадок claude code ні в комітах ні в коді» | Коміти без трейлерів. Генератор бере команду моделі зі змінної середовища. Інструмент названо лише тут |
| «запусти агентів щоб пришвидшити процес» | Три паралельні субагенти з розділеними теками й окремими `--output` |
| «нам тут пом потрібен?» → «нам потрібно використати всі best practices» | Агент спершу виміряв, як реально використовується POM, потім зібрав чеклист з офіційної документації. Наслідок: ESLint, крос-браузер, посилення CI |
| «запускай рев'ю» | Workflow: посилення → рецензент без звіту автора → виправлення лише перевірених знахідок |

### 3. Бриф субагента (структура)

Кожен бриф мав однакову структуру, бо субагент знає тільки те, що є в промпті:

1. **Що вже перевірено вживу:** `data-test`, тексти помилок, ціни, статус-коди. Прямо сказано, що це факти, а не здогадки.
2. **ID багів:** баг треба відтворити самостійно, перш ніж писати на нього тест.
3. **Запропонований дизайн** з дозволом відійти від нього, якщо пояснити чому.
4. **Обов'язкова верифікація:**
   - `--repeat-each=3`;
   - мутація кожного очікуваного значення, тест має почервоніти;
   - для кожного баг-тесту прибрати `test.fail` і показати, що падає саме перевірка бага.
5. **Формат звіту:** дослівний вивід і `EXIT`, окремо «що не перевірено», а також
   «твої помилки: не вигадуй і не пропускай». З цього розділу частково складено список нижче.

### 4. Промпти workflow

- **Рецензент:** «Ти не писав цей код і навмисно не отримуєш звіту авторів: читай сам код і перевіряй усе, що
  стверджуєш… Повідомляй лише знахідки з доказами. Порожній список — теж валідний результат».
- **Агент, що виправляє:** «Спершу спробуй спростувати знахідку… Якщо не підтвердилась — `refuted` з доказом».
- **Рецензент API** підняв власний мок-сервер з навмисними поломками (PATCH не зберігається, видалений
  ресурс віддає 410, падає `/auth`) і перевірив, чи тести це помітять. Тобто перевіряв самі тести.
- **Рецензент генератора** не викликав справжню модель. Він підставляв фейкову «модель» із заготовленими
  відповідями, щоб детерміновано перевірити захист від послаблення та коди виходу.

### 5. Промпт генератора

[generator/prompt.md](generator/prompt.md) і [generator/repair-prompt.md](generator/repair-prompt.md). Конвенції
й app map підставляються в шаблон; у [generator/README.md](generator/README.md) описано, чому правила
перевіряються кодом, а не лише промптом.

## Де агент помилився і як це помітили

Нижче лише реальні випадки з цієї роботи. Для кожного вказано, що саме сталося, як це помітили і що змінилося
після.

### 1. Проба читала DOM до завершення навігації

- **Що сталося:** перша Playwright-проба saucedemo знімала дамп одразу після `click()`. Дамп з підписом
  «inventory» насправді показував форму логіну, а список сортувань вийшов порожнім (`sort options: []`).
- **Як помітили:** URL уже був `/inventory.html`, а вміст не відповідав підпису.
- **Що змінилося:** друга проба чекає на елемент конкретної сторінки (`inventory-list`) перед кожним
  читанням. У CLAUDE.md з'явилося правило про web-first очікування.

### 2. TypeScript 7 замість сумісної версії

- **Що сталося:** на старті агент поставив `typescript@latest`, тобто 7.0.2 (нативний компілятор) і
  перевірив лише, що `tsc` проходить.
- **Як помітили:** коли за порадою Playwright додавали `@typescript-eslint/no-floating-promises`. З
  `npm view typescript-eslint peerDependencies` видно `typescript >=4.8.4 <6.1.0`, а
  `require('typescript').createProgram` у TS 7 повертає `undefined`.
- **Що змінилося:**
  - TypeScript 6.0.3;
  - Dependabot ігнорує мажорні оновлення TypeScript;
  - заодно `@types/node` 26 замінено на 22 під рантайм Node 22.

### 3. `test.fail()` на початку баг-тесту ховав би зламані тести

- **Що сталося:** головний агент сам запропонував у брифі для UI ставити `test.fail()` на початку тесту. UI-агент так і
  зробив, а агент API відійшов від брифу й поставив його після контролів.
- **Як помітили:** документація Playwright цього порядку не описує, тож головний агент перевірив семантику окремим прогоном
  (Playwright 1.65.1):

  | Сценарій | Статус |
  | --- | --- |
  | Контроль падає до `test.fail()` у тілі | `unexpected`: тест червоний, і це правильно |
  | Контроль пройшов, перевірка бага впала | `expected` |
  | Баг виправлено | `unexpected` («Expected to fail, but passed») |
  | Декларативна форма `test.fail(title, body)`, падає контроль | `expected`: зламаний контроль сховано |

- **Що змінилося:** правило 7 у CLAUDE.md. Баг-тести UI і генератора переписано в workflow. Перевірки багів
  тепер приймають будь-яке коректне виправлення.
- **Чим закінчилось:** наприкінці я замінив `test.fail()` на паркування, як у моїх робочих автотестах. Порядок
  «контролі окремо» лишився, але відкритий баг тепер дає `skipped` з фактичною помилкою в анотації, а
  виправлений баг дає звичайний зелений тест із позначкою «розпаркуй». Причина: репозиторій запускатимуть
  пізніше проти чужих стендів, і червоний прогін через чуже виправлення був би хибною тривогою.

### 4. Назва інструмента в повідомленні коміту

- **Що сталося:** правило вже діяло, але в тілі першого коміту з'явився рядок, що згадував файл інструкцій
  агента за назвою.
- **Як помітили:** після комітів головний агент перевірив `git log --format=%B | grep -iE "claude|co-authored|generated with"`.
- **Що змінилося:** повідомлення ще не запушених комітів переписано. Локальний `commit-msg` hook, який робив би
  цю перевірку автоматично, заблокувала система дозволів агента: вона сприйняла його як спробу приховати участь
  агента. Тому перевірку робив головний агент вручну, перед кожним комітом і пушем.
- **Про історію комітів:** перед пушем її зібрано за темами (каркас, UI, API, лінтер, CI, генератор, документи),
  тому вона не відтворює хронологію роботи. Наприклад, заміна TypeScript 7 на 6 потрапила одразу в перший коміт.

### 5. Тестові дані на спільному стенді без плану прибирання

- **Що сталося:** під час розвідки API агент створив кілька бронювань із некоректними даними на публічному
  restful-booker і лише потім спробував їх видалити, масово, за ID із попереднього виводу.
- **Як помітили:** система дозволів заблокувала масове видалення, бо з контексту не видно, що це саме наші записи.
- **Що змінилося:**
  - правило 6 у CLAUDE.md;
  - фікстура `client` запам'ятовує кожне прийняте бронювання й видаляє його в teardown;
  - агент API довів аудитом: 36 створено, 36 видалено, усі 36 повторних `GET` повернули 404;
  - подальші проби видаляють те, що створили, в межах того самого скрипта.

### 6. Один зелений прогін сховав дві гонки

- **Що сталося:** UI-тест сторінки деталей і згенерований TC-GEN-01 проходили в першій версії й мали зелений
  звіт.
- **Як помітили:** на етапі посилення.
  - **UI.** Агент блокував сторонні запити (Google Fonts і телеметрія Backtrace, за правилом «Only test what you
    control»), а потім прогнав 3 браузери × 3 повтори шість разів. Результати: 2 зелені прогони, 1 червоний з
    6 падіннями, 3 червоні з одним падінням.
    - 6 падінь дала прихована гонка в тесті сторінки деталей. Блокування змінило таймінги, і вона проявилась.
      Діагностика: проба таймінгу DOM, A/B-прогін, і зворотна перевірка: зі штучно сповільненою мережею гонка поверталась у старому коді й не поверталась у виправленому. Після цього тест
      виправлено в `ProductPage`.
    - Одиночні падіння: зависання завантаження сторінки самого saucedemo і клік у WebKit без навігації. Без
      блокування було те саме, а за 30 ізольованих повторів жодне не відтворилось. Тобто це шум публічного
      стенду, який у CI поглинає `retries: 1` і звіт показує як **flaky**.
  - **Генератор.** Агент зробив червону перевірку TC-GEN-01 з `--repeat-each=10` і отримав 6 падінь з 10: URL
    змінювався раніше, ніж SPA рендерила екран.
- **Що змінилося:**
  - обидва місця виправлено як помилки тестів, а не застосунку;
  - конвеєр генератора приймає тест лише після 3 проходів поспіль;
  - фінальна перевірка перед пушем робилась кількома повними прогонами поспіль, а не одним.

### Що знайшли незалежні рецензенти

Рецензенти не бачили звітів авторів. З 19 їхніх знахідок підтвердились 19: 16 виправили агенти, 3 у
спільних файлах (README, `tsconfig.json`) закрив головний агент. Найцінніші:

- **Генератор.** «Виправлення» від моделі могло проковтнути твердження, що падає, через `.then(undefined, () => undefined)`: код
  проходив усі обов'язкові перевірки й 3 прогони, а конвеєр повертав PASSED. Тепер це відкидається і правилом на рівні
  лексем, і перевіркою після проходу.
- **Генератор.** Якщо файл кейсу лежав поза репозиторієм, `result.json` записував абсолютний шлях з
  тимчасовою текою інструмента. Це пряме порушення вимоги «без згадок».
- **API.** Невдале прибирання бронювання в teardown баг-тесту поглиналось `test.fail()`, тобто витік даних на
  стенді лишився б непоміченим.
- **API.** Рецензент підняв мок-сервер, на якому PATCH не зберігає дані, і показав, що @smoke-тест цього не
  бачить. Тепер після PATCH іде перевірка через `GET`.
- **UI.** Кука сесії живе 10 хвилин, а `ui-setup` логіниться один раз. У CI з одним воркером пізні тести
  падали б на сторінці логіну. Тепер фікстура перелогінюється.

### Останнє рев'ю після «готово»

Коли головний агент відзвітував «готово, CI зелений», я попросив ще одну перевірку чотирма незалежними агентами:
чистий клон з GitHub, код UI, API з CI, генератор з документами. Критичних дефектів вони не знайшли, і з чистого
клону все відтворилось (`109 passed`). Але знайшлося близько 16 проблем середньої ваги, яких попередні раунди не
бачили. Усі підтверджено й виправлено:

- **UI.** Тест BUG-UI-02 читав стан сторінки один раз одразу після кліку. Після виправлення бага він міг дати
  хибний зелений. Тепер кожен крок чекає на один із двох видимих станів.
- **API.** Тайм-аут `DELETE` у прибиранні обривав цикл, і бронювання тихо лишалось на стенді. З ретраєм у CI
  такий витік закінчувався б як «flaky» при зеленому прогоні. Тепер залишки пишуться у файл, і окремий крок CI
  падає, якщо файл не порожній.
- **API.** Відповідь 5xx у баг-тесті зараховувалась як «відомий баг». Тепер перед `test.fail()` є контроль, що
  сервер відповів не 5xx.
- **Генератор.** Захист від послаблення обходився заміною перевірки на `expect(1).toBe(1)` і написаннями
  `test.info().fail()` чи `.rejects`. Додано правила і 8 юніт-тестів (разом 44).
- **Документи.** Речення з протилежним змістом у README, непрацюючі curl-команди в баг-репортах API, кальки з
  англійської.

Тобто зелений звіт означав лише, що пройшли ті перевірки, які на той момент існували.

Після виправлень я попросив зняти скріншоти кожного бага. Усі чотири підтвердились наочно (знімки в README), а
перша версія проби знову зняла стару сторінку: URL уже змінився, а екран ще ні. Це та сама гонка, що в помилці 1,
і зловив її вже сам знімок, а не цифри у виводі.

## Що спрацювало і що я зробив би інакше

- **Спрацювало:**
  - живі проби до першого тесту: локатори, тексти й маршрути взято з живого сайту, а не з пам'яті моделі, і баги
    знайдено ще на розвідці;
  - розділене володіння файлами й окремі `--output` для паралельних агентів;
  - вимога побачити кожен тест червоним і пройти 3 рази поспіль;
  - рецензент без звіту автора.
- **Зробив би інакше:**
  - перевіряти сумісність версій інструментів до першого коміту, а не після;
  - не пропонувати субагентам дизайн (як `test.fail` на початку), не перевіривши його семантику;
  - одразу закладати лінт і форматування як обов'язкову перевірку для згенерованого коду;
  - тримати робочі нотатки в репозиторії, а не в тимчасовій теці.
