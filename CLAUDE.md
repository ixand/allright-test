# Project rules for the coding agent

QA automation test task, Playwright + TypeScript.

- UI target: https://www.saucedemo.com, user `standard_user` / `secret_sauce`
- API target: https://restful-booker.herokuapp.com (contract: `/apidoc`)
- Bonus: `generator/` turns a plain-text test case into a runnable Playwright spec

## Commands

```bash
npm ci && npx playwright install --with-deps chromium firefox webkit
npm test                      # every project
npm run test:ui               # ui-chromium, ui-firefox, ui-webkit (+ ui-setup)
npm run test:api | test:generated
npm run test:smoke            # @smoke: the critical path only
npm run test:bugs             # @bug: known defects, parked (skipped while the bug is open)
npm run test:unit             # node --test for the generator's static checks and weakening guard
npx playwright test <file> --project=ui-chromium --reporter=list --retries=0
npm run check                 # typecheck + lint + format:check; CI runs the same three
```

## Layout

| Path | What lives there |
| --- | --- |
| `tests/ui/pages/` | Page objects, one per screen, plus small shared components; locators as readonly fields, actions as methods, no assertions |
| `tests/ui/fixtures.ts` | `test` extended with page objects, re-exports `expect` |
| `tests/ui/data/` | Users and catalog data (the expected values) |
| `tests/ui/auth.setup.ts` | Logs in once and saves `playwright/.auth/standard_user.json` |
| `tests/api/` | Booking client, fixtures with teardown, specs |
| `tests/support/` | `knownBug.ts`: parking a test on a registered bug |
| `tests/generated/` | Output of the generator. Hand edits must be recorded in `generator/examples/` |
| `generator/` | Pipeline script, prompt template, app map, examples |

## Writing tests

1. Locators: `getByTestId()` (`testIdAttribute` is `data-test`). saucedemo publishes a `data-test`
   attribute on almost every element the tests use, and the Playwright docs count test ids as an "explicit contract".
   Where the user-facing text is the behaviour under test (button label, error, heading), assert that
   text with `toHaveText`. Use `getByRole` for elements without a test id. No CSS chains, no XPath, no
   `nth()` unless the order is what is being tested. Locators live in page objects, not in specs
   (generated specs are self-contained by design, see `generator/README.md`).
2. No `waitForTimeout`, sleeps or `networkidle`. Use web-first assertions only (`await expect(locator)…`).
3. Tests are independent: each has its own context and its own data, and none depends on run order.
4. Every expected value has a source: the task, the apidoc, RFC 9110 for undocumented error codes,
   UI copy, or `tests/ui/data`. Never derive it from the value under test. Two stated
   exceptions: sorting, where the expectation is a sorted copy of the catalog data, and the 8% tax rate,
   which saucedemo publishes nowhere and was observed on the overview page.
5. Money is compared in integer cents, never as floats.
6. API tests delete every booking they create, in fixture teardown, negative tests included.
7. Known bugs are **parked**, not expected to fail:
   - Assert the **correct** behaviour, tag `@bug`, and add
     `annotation: { type: 'issue', description: 'https://github.com/ixand/allright-test#bug-xxx-nn' }`.
   - Run the positive controls first as plain assertions, then wrap only the bug assertion in
     `parkedOn('BUG-XXX-NN', '<symptom>', async () => { … })` from `tests/support/knownBug.ts`.
     While the bug is open the test is skipped with a note that quotes the failure. Once it is fixed
     the test simply passes and the report says to unpark it. A failing control is a real failure.
   - Do not use `test.fail()`: a fixed bug would arrive as a red run.
   - Hard assertions only inside `parkedOn`; `expect.soft` cannot be parked.
   - Accept every correct fix, e.g. any 4xx for a validation bug.
   - Register the bug in `README.md` under the same id.
8. Never weaken an assertion or change an expected value to get green. On a failure, first decide
   whether it is a test bug or an app bug, and show the evidence.
9. Tags: `@smoke` for the critical path (login, checkout, booking lifecycle), `@bug` for parked known defects.

## Definition of done for a test

- It passes 3 times in a row: `--repeat-each=3 --retries=0`. UI tests pass on all three browsers.
- It has been seen **red** once: break its expected value, run it, check that the failure points at
  that assertion, then revert.
- `npm run check` is clean.

## Shared sandboxes

Both targets are public. Run no load, create no data you will not delete, and never touch bookings
you did not create.

## Code and commits

- Conventional commits: `test(ui): …`, `test(api): …`, `ci: …`, `docs: …`.
- Do not add tool attribution, "generated by" lines or co-author trailers to commits, PRs or code comments.
- Comments explain *why*, not what.
